# ROADMAP.md — THE BASICS: Frontend → Django Full-Stack

Scope note: single-tenant app (one site, one set of content). No multi-tenancy, no Store/tenant model, no SaaS billing. `rule.md` §14 (multi-tenancy) and §19 (payments) do not apply unless a paid-tier feature is requested later — skip them.

Stack: Django 5+, PostgreSQL (prod) / SQLite (dev), Jinja2, Tailwind CSS, Alpine.js, HTMX, Django ORM, Django auth.

Current state (verified in repo): all "backend" is client-side —
- `api.js` → `MockDB` — hardcoded `pyqBank`/`mcqBank` arrays, localStorage-seeded users/progress/topics/daily question
- `storage.js` → `StorageManager` — localStorage bookmarks, attempts, topic stats, session resume
- `auth.js` → `Auth` — localStorage `tb_users`/`tb_session`/`tb_current_user` (built this session, still fake)
- `*-data.js` (polity, history, geography, economy, environment, ethics, governance, disaster-management, internal-security, ir, social-issue) — hardcoded subject/topic/lesson content, paired with `*-ui.js` renderers
- `mains-pyq-data.js` / `mains-pyq-logic.js` — mains PYQ bank + self-star-rating evaluation (no AI, no real scoring)
- `evaluate.html` / `my-evaluations.html` / `sample-evaluation.html` — mains answer upload + self/manual evaluation flow, not persisted server-side

Everything below replaces that with real Django apps + Postgres, keeping current HTML/CSS look (rule.md §5: preserve design).

## Deep audit — security, performance, roadmap recheck — and Docker/Postgres/Redis production setup (user request)

### Security

- [x] XSS audit — grepped every `|safe` filter across all templates (8 usages total). All 8 are on staff-managed content only (`Question.text`/`explanation`, `MainsQuestion.model_answer` fields) — never on user-submitted `Submission.answer_text`/`notes`, `Article.summary`, or `Post.body` (all auto-escaped, confirmed). The trust boundary is "staff can inject HTML into public pages," identical to how Django admin or any CMS already works — not a new vulnerability introduced by `apps.platform_admin`, just the same accepted trust model extended to a second editing surface.
- [x] **Real gap found and fixed: password reset was silently broken in production.** `prod.py` never set `EMAIL_*` — without it, Django falls back to its default SMTP backend with no host configured, so every `PasswordResetView` submission would raise in prod (never caught in testing, since dev always used the console backend). Added real `EMAIL_HOST`/`PORT`/`USER`/`PASSWORD`/`USE_TLS`/`DEFAULT_FROM_EMAIL` from env, matching the same "real value required in prod" pattern as `DATABASE_URL`.
- [x] **Real gap found and fixed: CSRF/HTTPS would break behind a reverse proxy.** No `CSRF_TRUSTED_ORIGINS` (Django 4+ requires the real origin(s) explicitly in prod) and no `SECURE_PROXY_SSL_HEADER` (without it, Django can't tell a proxied request was HTTPS, so `SECURE_SSL_REDIRECT=True` — already set since Phase 0 — would redirect-loop forever once actually deployed behind nginx). Both added, `CSRF_TRUSTED_ORIGINS` from env, `SECURE_PROXY_SSL_HEADER`/`USE_X_FORWARDED_HOST` hardcoded (correct for any reverse-proxy deployment, not just this one).
- [x] `python manage.py check --deploy --settings=config.settings.prod` — run against realistic env vars. Clean except the expected warning about the test-only `SECRET_KEY` I supplied for the check itself (a real deploy generates its own, documented in `.env.example`).
- [x] **Real bug caught before it could ship: `500.html` would have crashed while rendering the error page.** Django calls `server_error()` with no request and no context processors (deliberately, so a broken app can't also break its own error page) — a `500.html` extending `base.html` would hit `navbar.html`'s `request.user.is_authenticated` with no `request` object at all and raise `UndefinedError`, replacing a clean 500 page with an even worse crash. Caught by simulating Django's *exact* call pattern (`template.render()` with zero args) before shipping it, not by inspection. Fixed: `500.html` is fully standalone (inline styles, only the always-available `static`/`url` Jinja globals, no `base.html` extend). `404.html` *does* get a request from Django, so it safely extends `base.html` — verified live under real `DEBUG=False` + full middleware via `Client`, not `RequestFactory` (which skips `AuthenticationMiddleware` and gave a false failure on the first attempt — `request.user` genuinely is present by the time Django's URL resolver gives up and calls the 404 handler in the real request cycle).
- [x] No `csrf_exempt`, no hardcoded credentials, `DEBUG = True` only in `dev.py` — grepped to confirm, not assumed.
- [x] Non-root Docker user (see below) — a container running as root is a real, boring gap in a lot of shipped Dockerfiles; fixed here from the start.
- **Known gap, flagged not fixed**: no brute-force/rate-limiting protection on login or signup. Django has nothing built in for this; adding it means a new dependency (`django-axes` or similar) and real config decisions (lockout duration, per-IP vs per-account) that weren't asked for — noted here rather than silently added or silently skipped.

### Performance

- [x] **Real bug: `submit_answer` prefetched choices then never used the prefetch.** `Question.objects.prefetch_related('choices')` followed by `question.choices.filter(...)` — calling `.filter()` on a prefetched related manager bypasses the prefetch cache and re-hits the DB, so the two lookups (`selected`, `correct_choice`) cost 2 extra queries every single answer submission, on top of the wasted prefetch query itself (4 queries where 2 belong). Fixed: fetch once via the prefetch, then filter the resulting Python list for both lookups — genuinely 2 queries now, not 4.
- [x] **Real bug: `question_list` prefetched choices the list template never renders.** The list view only shows type/subject/difficulty/text — no choice ever appears on that page — so `prefetch_related('choices')` was fetching every choice for every matching question on every page load, unused, and the waste scales with content growth. Removed.
- [x] **Real gap: zero pagination anywhere on public list views.** `prelims:list`, `mains:list`, `current_affairs:list`, `blog:list` all loaded their *entire* filtered queryset unbounded — fine at today's 8-10 rows per table, a real problem once real content volume shows up (this is explicitly the highest-traffic feature per Phase 4's own notes). Added `Paginator` (20/page) to all four, with HTMX-aware prev/next controls that preserve the active filters through pagination — verified live that out-of-range and non-numeric `?page=` values both degrade gracefully (200, clamped to a valid page) instead of erroring, matching the same "never trust the client blindly" posture used throughout this project.
- [x] Redis wired into the cache framework (`CACHES` in `prod.py`, native Django 4.0+ `RedisCache` backend — no third-party `django-redis` needed) and put to real use: `footer_subjects` (Phase 10) ran a DB query on *every single page render site-wide*, including anonymous traffic — now cached 5 minutes, with a `post_save`/`post_delete` signal on `Subject` (`apps/content/signals.py`) invalidating it immediately on edit rather than leaving admins staring at a stale footer for up to 5 minutes after saving a change. Verified live, not just that it doesn't crash: confirmed the cache actually gets set on first render and returns the identical cached list on a second call within the same process, and confirmed the signal actually clears a manually-seeded cache value on `Subject.save()`.
- [x] `CONN_MAX_AGE=600` + `CONN_HEALTH_CHECKS=True` on the prod database connection — without this, Django opens a brand new Postgres connection on every request, real overhead under gunicorn's multiple workers that a stock Django prod setup very commonly ships without.

### Two flagged gaps, fixed (user follow-up)

**Brute-force login protection** — `django-axes` wired in (`AUTHENTICATION_BACKENDS`, `axes.middleware.AxesMiddleware` after `AuthenticationMiddleware`, migrated). Locks a username+IP pair out after 5 failed attempts for 1 hour (`AXES_FAILURE_LIMIT`/`AXES_COOLOFF_TIME`) — covers `accounts:login` *and* `/sd/`'s Django admin login automatically, since it hooks in at the authentication-backend level, not per-view.
- **Real version-mismatch bug caught immediately**: the class is `AxesStandaloneBackend` in the installed 8.3.1, not `AxesStandardBackend` as older docs/tutorials show — `manage.py check` failed loudly on the wrong name before it ever reached a test, fixed on the spot.
- **Real breakage found and fixed**: adding a second authentication backend broke `apps.accounts.views.signup` — `auth_login(request, user)` after creating a brand-new user (not via `authenticate()`) now needs an explicit `backend=` kwarg, since Django can no longer infer which of two backends to attribute the session to. Caught by the full test suite failing, not by inspection; fixed by passing `backend='django.contrib.auth.backends.ModelBackend'` explicitly, with a comment explaining why axes' own backend doesn't apply to this specific call site (the user just proved their identity by completing signup — axes' job is catching repeated *failures*, not gating this one).
- Verified live, adversarially, not just "doesn't crash": fired 5 wrong-password attempts against the real `test@example.com` account → 6th attempt returned `429` **even with the correct password** — genuine lockout, not a false positive. Also confirmed lockout is scoped to the (username, IP) pair as configured: a *different* username from the same IP was unaffected — deliberate, prevents one legitimate user being collaterally locked out because someone else on a shared IP (office NAT, etc.) got their own account locked. Reset via `manage.py axes_reset` afterward so the demo account wasn't left locked for the user.

**Automated Postgres backups** — new `backup` service in `docker-compose.yml` (`docker/backup.sh`, running inside the `postgres:16-alpine` image for its bundled `pg_dump`, no extra image needed). Dumps daily (`pg_dump | gzip`) into a new `postgres_backups` named volume, prunes anything older than `BACKUP_RETENTION_DAYS` (default 14, env-overridable). A plain sleep-loop, not real cron — a minimal Alpine container running actual cron needs its own daemon/logging setup for no benefit at this scale.
- **Redis deliberately still has no backup — stated explicitly, not an oversight.** Redis in this stack holds exactly one thing: the `footer_subjects` cache (5-minute TTL, rebuilt from Postgres on the next request either way). Backing up a cache is backing up nothing — there's no data there that isn't already durably in Postgres. If Redis ever starts holding real state (sessions, something without a Postgres source of truth), that call needs revisiting; today it doesn't.
- Honest limit on this fix, same as the section above: the backup volume lives on the *same host* as the database it's backing up. That protects against `docker compose down -v`, a bad migration, or an accidental `DROP` — it does not protect against losing the host entirely (disk failure, the VM getting deleted). Shipping off-host copies (S3, another server, etc.) needs real storage credentials this environment doesn't have — flagged precisely, not silently left as "backups: done."
